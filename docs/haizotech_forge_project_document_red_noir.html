Project Overview · Base Platform + Forge v2

HaizoTech — the platform, plus Forge

A single monorepo running a credibility-first public marketing site, an internal admin dashboard, and a shared backend — now extended with Forge: five features that turn scoping and delivery into something the client experiences directly, instead of something they're told about.

Next.js 15 · Express · Prisma · Socket.IO Phases 0–8 complete 5 new Forge features, additive only Design tokens: white + blue

01 · The Project Idea

Make the pitch and the platform the same thing

The base problem. The original haizotech.com read as a dark web3/AI template — a clipped hero, gradient orbs, fabricated testimonials. For an agency selling to healthcare, fintech and SMB clients, that actively lowered trust. The redesign's wedge is real work, plainly shown: a white, blue-accented, credibility-first site backed by an admin dashboard the team can run without touching code, and a backend with a locked, contract-validated API so the two never drift apart.

The Forge idea, layered on top. Even a redesigned brochure site still makes a prospect wait: fill out a form, wait for a call, wait for a quote. Forge removes that wait. A visitor gets a real complexity tier in 30 seconds, then a real budget and timeline band by moving sliders themselves — before they've talked to anyone. Once they're a client, that same transparency continues: a live portal that replaces status-update emails, and a bookmarkable, zero-login status page that's always current. The five Forge features aren't a separate product bolted on — four of them are one continuous funnel from first visit to final delivery, built additively on the existing Phase 1–8 stack with no breaking changes.

In short: the base platform makes HaizoTech look trustworthy. Forge makes that trust checkable — the client scopes their own project, watches the same board the team works from, and never has to ask "any update?" again.

Decisions worth knowing

The tokens live in exactly one file.

packages/config/theme.css is ported verbatim from the approved Phase 0 prototype. No app or component may write a hex value — that's what keeps both frontends looking like one product, and makes a future dark theme one block instead of a rewrite.

The OpenAPI spec is hand-authored and canonical.

backend/openapi/openapi.yaml is the source of truth; packages/types is generated from it and committed. CI fails three ways if they diverge: the spec must lint, regenerating must produce no diff, and response validation runs in dev and test.

The database schema only ever grows.

schema.prisma is the live production schema, extended additively — no renames or drops until 30 days after cutover. That constraint is the entire rollback plan: the old code still runs against the new schema, so cutover is an nginx change and rollback is the same change backwards.

Auth is HttpOnly cookies, not localStorage.

The previous admin kept its JWT in localStorage, readable by any XSS; the socket layer read it from there too. Cookies are sent on the WebSocket handshake, so one mechanism covers both paths — which is why all three apps sit under one registrable domain.

Layering is enforced, not suggested.

routes → controllers → services → repositories. Controllers do HTTP and nothing else; repositories are the only code that touches Prisma — the previous backend put everything in controllers, which is why nothing was testable.

03 · Design System

White-dominant, blue as accent

05 · New — Forge Feature Flow

Five features, one connected platform

A scoping quiz that feeds a unified risk simulator, a client portal that replaces manual status emails, a live delivery-pulse page clients can bookmark, and an interactive query-plan diagram for the engineering blog. Everything builds additively on the existing Phase 1–8 stack — no breaking changes.

01 Complexity Estimator⟶ 02 Scoped Risk Simulator⟶ 03 Client Portal⟶ 04 Delivery Pulse
05 Query Plan Diagram sits outside this funnel — it's blog content tooling, not part of the delivery loop.
01
Public · Entry point

Complexity Estimator

A 5-question triage quiz. No sliders, no numbers — just a tier in under 30 seconds, before a visitor commits to filling out a form.

User flow

01
Land on estimator

Linked from Services and Contact: “Not sure what tier your project is? 30 seconds.”

⟶
02
Answer 5 questions

Plain-language, tap-to-answer — no numbers, no jargon (e.g. “Will people log in with different permission levels?”).

⟶
03
Tier computed

Weighted answers map to Simple / Standard / Complex / Enterprise, client-side, instantly.

⟶
04
Two paths offered

“Send this as an enquiry” or “Get a real budget/timeline band” — the second opens the Scoped Risk Simulator pre-seeded with these answers.

⟶
05
Result logged

Tier + answers stored even if the visitor leaves — a lightweight, anonymous top-of-funnel signal.

Data flow

5 quiz answers (client) → TierEngine.score() → tier-weights.json (admin-editable) → POST /v1/estimates → EstimateController → EstimateService → Estimate (Postgres)

What gets added

LayerAddition
DatabaseNew table Estimate (answers JSON, tier, sourceIp-hash for dedupe, optional convertedInquiryId) — purely additive.
BackendEstimateService + EstimateRepository; route POST /v1/estimates; admin route PUT /v1/config/tier-weights for no-deploy tuning.
Public frontendStandalone quiz component linked from Services and Contact; hands answers to the Risk Simulator as pre-filled sliders.
Admin frontendFunnel widget on the dashboard: estimates started vs. converted to enquiry, by tier.
OpenAPIEstimate schema added to openapi.yaml; types regenerate into packages/types.
02
Public + Admin · Merged

Scoped Risk Simulator

One engine, two surfaces. Public scope sliders produce a real budget/timeline band. The same engine re-scopes live projects in admin and previews the risk impact live — no separate tool.

User flow

01
Arrive pre-seeded

Sliders open already set from the Complexity Estimator's answers, or from scratch.

⟶
02
Adjust levers

Roles, integrations, real-time needs, compliance, timeline pressure.

⟶
03
Instant estimate

Client-side calc against a versioned weight table — no round trip.

⟶
04
Send as enquiry

One click posts the exact scenario JSON into the contact form, pre-filled.

⟶
05
Admin re-scope

A project manager opens the same What-If panel on a live project; a nightly cron scores every active project and fires a threshold alert through the existing bell + digest system.

Data flow

Slider change → ScenarioEngine (client) → scenario-weights.json → POST /v1/scenarios → ScenarioService → Scenario (Postgres) ··· Cron (nightly) → RiskService.computeAll() → Kanban/Chat/Milestone repos → ProjectRiskSnapshot → NotificationService

What gets added

LayerAddition
DatabaseScenario (inputs JSON, computedBand, nullable estimateId/inquiryId/projectId) + ProjectRiskSnapshot (projectId, axis scores, computedAt) — both additive.
BackendScenarioService + RiskService share the scoring model. Routes: POST /v1/scenarios, GET /v1/projects/:id/risk, GET /v1/projects/:id/risk/history. RiskService.scoreHypothetical() is a pure function, no DB write, used for live admin preview.
Admin frontendUnified What-If + Risk panel on the project detail page; radar chart + trend lines; compact risk badge on the project list and Kanban headers.
Public frontendScope-slider component on the services/contact flow, pre-seeded from the Estimator handoff.
NotificationsNew type risk.threshold_crossed, routed through the existing Phase 5 bell + digest system.
03
Client-facing · New

Client Portal

A secure, persistent login for clients — their Kanban, milestones, approved files, and a direct message thread to the team. Replaces status-update emails entirely.

User flow

01
Admin invites client

One button on the project page sends a signed invitation email; client sets their own password.

⟶
02
Client logs in

A separate login path (/client/login) issues a client-scoped JWT that structurally cannot touch any staff route.

⟶
03
Sees their project

The Kanban columns the admin whitelisted, milestones, client-visible files, and a message thread to the team.

⟶
04
Sends a message

Lands in the existing Conversation model — the team sees it in the admin chat view, in real time over the existing sockets.

⟶
05
Gets notified

Email on a reply or a published milestone; one click brings them straight back in.

Data flow

Admin sends invite → POST /v1/client-auth/invite → ClientAccount (Postgres) → Mailer ··· Client login → POST /v1/client-auth/login → ClientJWT (scoped) → GET /v1/client/projects/:id → filtered Column + Task + Milestone (clientVisible=true only)

What gets added

LayerAddition
DatabaseNew table ClientAccount (email, passwordHash, projectId FK, inviteToken, inviteExpires) — entirely separate from User. Column gets clientVisible Boolean. Attachment gets visibility String. New table Milestone (projectId, title, targetDate, completedAt, clientVisible).
BackendNew ClientAuthController + ClientProjectController. Client JWT uses a separate secret and a sub claim prefixed client: so middleware can never mistake it for a staff token.
SocketClient joins room client_; staff joins the same room from the admin chat view. Reuses the existing Phase 7 Conversation model with a new type: "client_channel".
Client frontendA dedicated route group under /client — separate session store, separate layout. No admin components imported.
Admin frontendInvite button + per-column/per-file visibility toggles on the project detail page; a “Client Portal” preview tab.
04
Client-facing · New

Client Delivery Pulse

A zero-login, token-gated status page auto-generated from real project data. The client bookmarks one URL and sees live progress without ever asking.

User flow

01
Admin shares link

One click on the project page generates a signed, expirable Pulse URL — sent however's convenient.

⟶
02
Client opens it

No login. The signed token in the URL authenticates the request server-side.

⟶
03
Sees live data

Task completion rate, current phase, milestone timeline, budget band — pulled from real platform data at render time.

⟶
04
Bookmarks it

The URL stays valid until the admin rotates it or the project closes; the page is always current, never stale.

⟶
05
Portal upgrade prompt

A subtle CTA: “Want to message the team directly? Ask us to set up your Client Portal.”

Data flow

Admin generates link → POST /v1/projects/:id/pulse-token → PulseToken (Postgres) ··· Client opens URL → GET /v1/pulse/:token → PulseService.resolve() → Project + Column + Task + Milestone + RiskSnapshot → SSR Pulse page

What gets added

LayerAddition
DatabaseNew table PulseToken (projectId FK, token, expiresAt, createdById) — a short-lived signed JWT, revocable/rotatable by admin at any time.
BackendPulseService assembles a read-only project snapshot from existing repos. Routes: POST /v1/projects/:id/pulse-token (admin), GET /v1/pulse/:token (public — the signed token in the path is the credential, no auth middleware needed).
Public frontendStandalone SSR page at /pulse/[token] in the public Next.js app — no shared session with the Client Portal.
Admin frontend“Generate Pulse link” button on the project detail page, with copy and rotate/invalidate controls.
OpenAPIPulseToken and PulseSnapshot response schemas added to openapi.yaml.
05
Public · Blog

Query Plan Diagram

Turns pasted EXPLAIN ANALYZE JSON into an interactive, collapsible plan tree embedded in technical blog posts — no screenshots, no external charting service.

User flow

01
Run EXPLAIN

Author runs EXPLAIN (ANALYZE, FORMAT JSON) on the query being written about.

⟶
02
Paste into admin

A “Query plan” field on the blog post editor accepts raw JSON.

⟶
03
Validate + store

Backend checks it parses as a real plan shape before saving; an optional second field enables a before/after toggle.

⟶
04
Post renders

The renderer detects the plan field and mounts an interactive tree; a reader expands nodes for rows, cost, actual time, buffers, with the hot path auto-highlighted.

Data flow

Admin editor (paste JSON) → PUT /v1/blog/:id → PlanValidator (shape check) → BlogPost.queryPlan (jsonb) → Next.js blog page (SSR) → <QueryPlanTree /> client component

What gets added

LayerAddition
DatabasequeryPlan and queryPlanBefore jsonb columns added to the existing Blog model — additive, no migration risk.
BackendLightweight PlanValidator in the blog service rejects malformed JSON on save; no new table.
Admin frontendTextarea + “validate plan” control added to the existing blog post editor.
Public frontendNew component in packages/ui, reusable outside the blog.
OpenAPIqueryPlan field added to the BlogPost schema; generated types flow into both frontends.

06 · How It All Connects

From first visit to final delivery

01 Complexity Estimator⟶tier + answers⟶ 02 Scoped Risk Simulator⟶scenario → Inquiry → Project⟶ 03 Client Portal⟶live throughout delivery⟶ 04 Delivery Pulse

A lead's estimator tier seeds the What-If scenario, which becomes the project's baseline scope and its nightly risk benchmark. Once the project is live, the client gets two complementary windows into it: the Client Portal for active collaboration — messaging, Kanban, milestones — and the Delivery Pulse for passive, no-login check-ins from a bookmarked link. The Pulse surfaces a prompt to upgrade to the full Portal for clients who want more.

05 Query Plan Diagram is the deliberate exception: content tooling for the engineering blog, touching only the Blog model, intentionally outside this loop.

Underneath all of it: the same base platform decisions still hold — one design-token file, one OpenAPI contract, an additive-only schema, and HttpOnly cookie auth extended (not replaced) by a structurally separate client-scoped JWT.
